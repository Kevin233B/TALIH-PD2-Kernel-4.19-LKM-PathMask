# Linux 4.19 compat

This branch carries the minimal compat changes needed to build `pathmask.ko`
and `procguard.ko` against an arm64 **Linux 4.19** kernel (developed and
verified on a MediaTek MT8797 Android kernel, clang r383902, out-of-tree
`make M=... modules`).

Base: upstream `259e7bab9a41` ("release: 2.8.0").

## Changes

### kernel/pathmask.c
- `regs_set_return_value()` only exists from kernel 5.9. On arm64 before that
  the syscall return value lives in `pt_regs->regs[0]` — exactly what the
  5.9 helper writes — so a shim macro is added for
  `LINUX_VERSION_CODE < KERNEL_VERSION(5, 9, 0)`.

### kernel/procguard.c
- same `regs_set_return_value` shim, plus a missing
  `#include <linux/version.h>`.

## Status

Both modules compile and link into `pathmask.ko` and `procguard.ko` against
Linux 4.19 arm64 with clang, and every undefined import (including
`register_kprobe` / `register_kretprobe` / `unregister_kprobe` /
`unregister_kretprobe`) resolves against the target kernel's
`Module.symvers`.

A subtle failure mode is worth recording: with `CONFIG_KPROBES=n`, 4.19's
`include/linux/kprobes.h` defines `register_kprobe()` / `register_kretprobe()`
as `static inline` stubs returning `-ENOSYS`. The module then still compiles
**with zero warnings** — the calls are inlined and the entire kprobe
machinery is eliminated as dead code, so the `.ko` carries no kprobe imports
at all — but `insmod` fails with `-ENOSYS` and the mechanism never exists.
A clean compile therefore proves nothing about loadability here; the kernel
must be built with `CONFIG_KPROBES=y` for the imports (and the machinery
behind them) to be real.

Deployment notes for any consumer:
- the `.ko` must be paired with the kernel build it was produced against
  (vermagic and symbol CRCs must match), and
- the producing kernel must have `CONFIG_KPROBES=y` (see above for why the
  compile alone proves nothing).
